## 21. v1.11.1: 속도 — 결과는 비트 하나 그대로

대실험 전에 엔진을 빠르게 했다. 조건은 "결과가 비트 하나도 바뀌지 않는다".

### 같은 결과의 확인

| 확인 | 결과 |
|---|---|
| `node cli.js suite` (88줄, 1.11.0 기준) | 바뀐 줄 없음 (한 줄로, 일꾼 4 모두) |
| 녹화 넷의 해시 (중간 판단 수준 쌍, risk + 몸 묶기 / 화약통) | 넷 모두 같음 |
| 457판 결과·기록 해시 (규칙 다섯 묶음 × 평범·중간·대마법사 × 판단 다섯 × 덱 셋, 둘러싸기 셋) | 같음 |
| 260판 해시 (모든 덱·판단 수준·부류·규칙을 섞고 2대2 포함) | 같음 |
| 망토 30판 | 같음 |
| 헤드리스 Chromium 194판 = Node | 같음 |

고치는 동안 이 해시가 세 번 틀렸고(주석이 문장을 삼킨 것 둘, 제자리 거르기 뒤 한 줄) 그때마다 바로 잡혔다.

### 속도 (이 기계: 4 vCPU VM, Node 22.22.2)

VM이라 같은 측정도 ±20% 흔들린다. 그래서 **두 판(1.11.0, 1.11.1)을 한 프로세스에 올려 번갈아** 21번 돌려 가장 빠른 값과, 짝마다 비의 중앙값을 함께 본다.

| 대진 (데워진 뒤) | 1.11.0 | 1.11.1 | 배 (가장 빠른 값 / 짝 중앙) |
|---|---|---|---|
| 평범 전설끼리 10판 | 0.25 ms/게임초 | **0.053** | 4.7 / 5.1 |
| 평범끼리(판단 수준 없음, 합법 최강 대 기본기) 20판 | 0.065 | 0.033 | 2.0 / 2.1 |
| 중간 대가 대 상급, risk + 몸 묶기 20판 | 0.46 | 0.14 | 3.4 / 3.6 |
| 대마법사(광역) 1 대 평범 100(기본기), 둘러싸기 6판 | 0.54 | 0.29 | 1.85 / 1.85 |

| 새 프로세스에서 한 판 (JIT가 데워지지 않은 채, 11번의 중앙값) | 1.11.0 | 1.11.1 | 배 |
|---|---|---|---|
| 평범 전설끼리 (120 s 판) | 127 ms (1.06 ms/게임초) | 89 ms (0.74) | 1.4~1.7 |
| 대마법사 1 대 평범 100 (24 s 판) | 129~145 ms | 129~135 ms | 1.0~1.1 |

| 병렬 (`par.js`) | 일꾼 1 | 일꾼 2 | 일꾼 4 |
|---|---|---|---|
| 평범 전설 대 대가 1600판 (10판씩 160 일감) | 12.3 s | 6.3 s | 4.1 s (3.0배) |
| 표준 묶음 88줄 | 23.6 s | 17.2 s | 17.0 s |
| (참고) 1.11.0 표준 묶음, 한 줄로 | 78.8 s | | |

`node cli.js bench`의 1대1 한 판은 8~10 ms → 약 4 ms.

**목표와 견주면**: 평범 전설끼리 "게임 1초당 0.5 ms 이하"는 데워진 뒤(0.053)로는 넉넉히 넘었고, 새 프로세스의 첫 판(0.74)으로는 못 미쳤다. 1 대 100 "지금의 절반 이하"는 데워진 뒤 0.54배(1.85배 빠름)로 조금 모자라고, 첫 판은 거의 그대로다. 대실험처럼 많은 판을 돌리면 데워진 쪽이 맞고, 병렬 실행기로 코어 수만큼 더 빨라진다(이 기계에선 표준 묶음이 2개 넘게는 잘 늘지 않았다. 따로 띄운 프로세스 넷도 17.2 s로 같아, 실행기가 아니라 이 VM이 계산이 아닌 메모리 쪽에서 막히는 것으로 본다. 순수 계산은 일꾼 넷이 같은 시간에 끝났다).

### 무엇이 느렸나

- **판단 400줄 한 덩어리**: TurboFan이 `think` 하나를 최적화하는 데 175~400 ms가 걸렸고(짧은 판 전체보다 길다), 도중에 객체 모양이 바뀌면 그것도 버렸다. 짧은 실행 내내 느린 코드로 돌았다. 조각으로 나누자 조각마다 5~40 ms에 된다
- **모양이 여럿인 객체를 읽기**(V8의 megamorphic IC가 전체의 15~30%): 마법 82개가 51가지 모양, 사람 객체에 판 중에 칸이 붙음(`bigp`·`lureT`·`emptyT`…), 몸 효과를 `delete`해 사전 모양이 됨, 상태를 `for-in`으로 줄임, 판단마다 `Object.assign`으로 새 성향 객체
- **덱이 정하는 값을 판단마다 다시**: `maxRange`는 후보마다·바위마다 불렸다. 결정론 `pow`(급수)가 추정 피해·크기(`C^0.4`)·위력(`C^K`)·신호 세기에서 판단·걸음마다
- **배열 `length` 대입**: 걸음마다 여섯 번 제자리 거르기와 적 목록 비우기의 `length =`가 C++ 쪽 느린 길로 가서 전체의 약 7%였다(바뀔 때만 넣게 했다)
- **걸음마다 새 배열**: `for (const slot of ['cast', 'castB'])`는 사람마다 걸음마다 배열을 만들었다. 녹화하지 않아도 효과 배열(`fx`)을 만들고 걸음 끝에 버렸다

### 해 보고 버린 것

| 시도 | 결과 |
|---|---|
| 마법 모양 맞추기를 한 칸씩 넣어서(`o[k] = s[k]`) | 0.8배로 느려졌다: 칸을 하나씩 넣으면 V8이 사전 모양으로 바꾼다. 객체 리터럴로 만드니 1.15배 빨라졌다 |
| 세계를 만들 때 마법 82개를 모두 사본으로 | 세계 만들기가 11 µs → 339 µs. 책에 든 마법만 사람을 넣을 때 사본으로 |
| 판단 조각의 공유 값을 반복으로 채운 객체에(`K[k] = null`) | 사전 모양이 되어 두 배 느려졌다. 리터럴로 |
| 숫자 칸을 만들 때 소수로 한 번 넣었다 되돌리기(모양 길들이기) | 첫 판도 데워진 뒤도 차이 없음. 뺐다 |
| V8 단계 올리기 문턱을 낮추는 옵션, Maglev | 첫 판이 빨라지지 않았다 |

```
node cli.js suite              # 결과가 같은지 (바뀐 줄 없음이어야 한다)
node cli.js suite --jobs 1     # 한 줄로
```
